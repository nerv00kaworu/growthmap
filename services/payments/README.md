# GrowthMap payments v1 candidate

## Reviewed public-config boundary

`config/commercial-public-config.json` is strict-validated and deterministically expanded by `tools/generate-public-config.py`. Its raw bytes must also match `config/commercial-public-config.sha256`, an independent reviewed pin that the generator never writes. Any canonical edit requires an explicit pin update under independent review; generated artifact or self-generated server digest updates are not approval. Required Linux and Windows CI run `python3 tools/generate-public-config.py --check` plus the full payments suite.

Independent FastAPI/SQLite candidate. Run tests only:

```sh
PYTHONPATH=services/payments:src/backend src/backend/venv/bin/pytest -q services/payments/tests
```

A pinned x402 2.17 `OfficialX402Facilitator` candidate adapter exists, but the approved Base recipient is pinned in strict public config and must be explicitly supplied in production. The selected no-account provider route is PayAI at the byte-exact origin `https://facilitator.payai.network`; `OfficialX402Facilitator.from_payai_provider(...)` constructs only that endpoint. Its public `/supported` snapshot is bounded and validated for x402 v2 `exact` on Base, but the returned digest and signer list are evidence only. Neither that snapshot nor `from_client_provider(...)` is an authorization boundary. No constructor, marker, subclass, provider, client, `/verify`, or `/settle` response proves production authorization; the real reviewed composition-root authorization is not integrated. The ledger never accepts renderer/request credentials, reads raw facilitator secrets, or accepts raw secret values from env. PayAI's current free tier requires no API key, removing the CDP-account blocker; deployment authorization, independently authenticated finality, Authority transport/custody, and live smoke evidence remain external blockers. There is no PayPal API, production credential, or private key in this candidate. `GROWTHMAP_PAYMENTS_ENV=production` remains hard-blocked until the reviewed Argon2id session provider is integrated; invalid recipient placeholders always fail, and the approved public recipient alone does not make production ready. Never copy either payment or authority DB into the desktop DB.

Operations: stop writes or use SQLite online backup API; copy DB plus `-wal`/`-shm` consistently, encrypt, restrict access, test restore and `PRAGMA integrity_check`. Current migration version is `PRAGMA user_version=13`; baseline 001 is immutable and forward remediations are checksum-pinned 002–013; apply reviewed forward-only migrations before service startup.

### Whop durable ingress source slice (schema 13)

`POST /v1/webhooks/whop` is a bounded, fail-closed local core only. It does **not** implement or guess Whop signature semantics. A caller-injected, independently reviewed verifier must authenticate the bounded raw request and return authenticated bytes before strict semantic parsing or storage; no verifier returns 503. The inbox stores only an immutable SHA-256 raw digest and bounded provider references, never the raw body or signature secret. Duplicate event IDs are idempotent, conflicting replays fail closed, retries are bounded, and terminal refund/dispute/chargeback states cannot be resurrected by late paid events. Paid events deliberately cannot create payment evidence or entitlement from an unreviewed Whop checkout/amount binding. Production composition remains unconditionally blocked and this source slice is not production-ready.

A caller-injected `OfficialWhopVerifier` source adapter now lazily imports the official
`whop-sdk`, passes the bounded UTF-8 body text unchanged to
`client.webhooks.unwrap(text, headers=...)`, and only then strictly normalizes the
documented `payment.succeeded` v1 envelope. Construction requires exact server-only
API/webhook secrets plus reviewed company, currency, total, and at least one exact
product/access-pass, plan, or checkout-configuration identifier; every configured
identifier is bound, as is `metadata.order_id`. Only the three standard headers
`webhook-id`, `webhook-timestamp`, and `webhook-signature` are admitted. The adapter
is never constructed by `create_app()`/`from_env()` and cannot lift the production
hard block. `refund.created`, `dispute.created`, and `dispute.updated` deliberately
fail closed: their exact payment/order linkage schema has not been established in
reviewed official documentation. No `whop-sdk` dependency was added to the lock:
there is no locally established, reviewed package version/API pin and packages were
not installed. Until that dependency is independently pinned and supplied, the
runtime adapter fails closed; deterministic tests use only the explicit SDK factory
seam and never bypass post-verification normalization.


Historical schema v4 authenticated terminal settlement evidence with HMAC-SHA256 using a dedicated external secret loaded only from `GROWTHMAP_SETTLEMENT_MAC_KEY_FILE` (minimum 32 bytes). The key is not stored in SQLite, logs, APIs, licenses, desktop artifacts, or packages. Loss of this key makes durable evidence unrecoverable and startup fails closed; key rotation requires a separately reviewed atomic re-MAC migration and is intentionally out of scope. Terminal settlement rows are database-trigger immutable except the evidence-preserving `settled` → `finalized_paid` transition. Release remains **NO-GO pending fresh independent review and Windows package-verifier CI**.

### R6 authenticated issuance closure
Assume SQLite rows and schema/triggers are attacker-controlled. The attacker is not assumed able to access the external MAC key file or authenticated checkpoint file. Configure both `GROWTHMAP_SETTLEMENT_MAC_KEY_FILE` and `GROWTHMAP_SETTLEMENT_CHECKPOINT_FILE`; the latter is a path, never secret material. Startup and every protected recovery/license/admin/PayPal/allocation operation verify checkpoint v2 over the normalized security schema and all rows in orders, proofs, provider events, intents, audit, migration ledger and checkpoint anchor. Trusted commits publish the authenticated next-state checkpoint while holding the SQLite writer transaction, then commit the DB; either crash ordering leaves a detectable mismatch and fails closed. Triggers are defense in depth. Historical paired DB+checkpoint replay is not prevented without an OS/HSM monotonic service, so production remains NO-GO. v5/v6 quarantine all legacy terminal evidence for operator inspection; no legacy row is auto-authenticated or issued.

## Device-bound activation candidate (schema 8)

The service is an evidence ledger/outbox, not a license signer. Official runtime dependency is hash-locked separately in `requirements.lock` as `x402[httpx]==2.17.0`; do not install this lock into the editor backend. Production construction remains hard-blocked. The candidate PayAI seam accepts only the exact canonical origin above and returns a client object with `verify`/`settle`; it does not expose a credential loader to HTTP requests or env. For initial low-volume beta, finality reads are pinned to Base's official `https://mainnet.base.org` endpoint. `OfficialBaseRPCTransport` exposes only chain ID, receipt, canonical-block and finalized-block reads; send/sign/debug/log-scan methods are forbidden, request/response sizes and timeouts are bounded, DNS answers must be globally routable, and any outage/rate limit/malformed reply fails closed. Base documents this public endpoint as rate-limited and not suitable for scaled production traffic, so the transport must be replaced when usage grows without changing ledger semantics. `MockFacilitator` and offline provider fixtures are explicit test infrastructure and are rejected/not wired in production.

After durable paid evidence, `entitlement_outbox` delivers `(x402, order_id)` idempotently into `LicenseAuthority.external_entitlements`. Because these are distinct SQLite files, delivery is intentionally at-least-once with UNIQUE inbox/outbox identities—not falsely atomic. Restart recovery may finalize only already-authenticated paid evidence and pending outbox records; unknown settlement remains `manual_review` and is never blindly retried.

The claim endpoint is POST-body-only and requires order recovery authentication, device public key, fresh nonce, and Ed25519 device proof. It returns only a schema-v2 device activation certificate. Legacy `license_json` columns remain readable only for controlled migration of pre-schema-8 rows; new flows never call the removed portable `_license()` signer.

SDK 2.17 settle success is not represented as chain finality: the SDK response has no receipt/block/finality timestamp. The adapter never substitutes `datetime.now()` and never retries settlement automatically. Schema 12 preserves the returned transaction only as an immutable `settlement_candidates` lookup hint bound to the prepared intent, verified payer, Base network, exact amount, source and response digest; recording it moves the order to manual review but cannot create a payment proof, allocate a sale or enqueue an entitlement. An authenticated receipt reconciler must independently promote it. `SignedFinalityReconciler` accepts an Ed25519-signed finality envelope under an independently pinned public key, so the payment process need not hold the sidecar signing key. `AuthenticatedUnixJSONClient` additionally authenticates bounded one-request-per-connection Unix-socket transcripts; it does not replace the operation signature or authorize startup. `AuthenticatedFinalityReconciler` retains the previously reviewed MAC-envelope compatibility path and accepts bounded bytes only from an injected external provider, strictly rejects duplicate/case-colliding/extra/missing/wrong-type JSON, and verifies HMAC-SHA256 in constant time over canonical JSON with domain `growthmap-authenticated-finality-v1`. It reuses the external settlement MAC trust root without reusing its checkpoint/evidence domains, and binds exact paid/unpaid outcome, transaction semantics, proof, nonce, order, payer, network, asset, payee, amount, evidence digest, source, UTC finality time and basis before calling the existing durable reconciliation contract. Provider transport/JSON is never itself trusted. Finality and Authority use separate Unix sockets and separate mode-0600 transcript keys. The Authority client exposes only handshake, entitlement/revocation crossing, and durable readback; it cannot create arbitrary licenses or access activation/admin methods. Key rotation still requires the separately reviewed external trust-root rotation procedure; no production provider is wired by `from_env()`. Schema-8 entitlement and schema-9 revocation outbox triggers make payload/delete/ack mutation fail closed; authority entitlement and deterministic revocation receipt inbox rows are likewise immutable. Leased/fenced workers reclaim expired leases, reject stale workers, back off/quarantine failures, and safely replay Authority-commit/payment-ack crashes.

Payment creates immutable revocation events only within five minutes of its aware service clock. Authority accepts a first-seen event only within a 24-hour transport window and five minutes of clock lead; a naive Authority clock fails closed. Authority checks an exact prior request digest before freshness so a commit/ack crash can replay the same receipt even after the window; first-seen stale/future events and contradictory replays fail closed.

### Live-recipient safety

`production` requires the exact reviewed public Base payee before any other credential gate. `test` and `development` reject that live payee by default; a deliberate integration run may opt in only with `GROWTHMAP_ALLOW_LIVE_PAYMENT_RECIPIENT=1` (all other values fail closed). Isolated tests must use a non-live fixture recipient.

The reviewed source is `config/commercial-public-config.json`. Run `python3 tools/generate-public-config.py` after review and `python3 tools/generate-public-config.py --check` in verification; generated server/desktop artifacts and the server SHA-256 pin must not be hand-edited.

Authenticated finality uses exact lowercase `0x` payer and transaction forms, exact lowercase configured asset/payee comparisons, and canonical UTC timestamps in `YYYY-MM-DDTHH:MM:SS[.ffffff]+00:00` form: zero microseconds have no fractional component and nonzero microseconds have exactly six digits. Evidence finality cannot predate the durable intent creation time. Equivalent `Z`, nonzero-offset, naive, future, and noncanonical spellings fail closed. Facilitator origins are byte-exact canonical `https://` + lowercase public-DNS host strings with no optional slash, port, userinfo, path, query, fragment, trailing dot, IP literal, localhost, or special-use hostname. Every ASCII whitespace/control byte (`0x00`–`0x20`, `0x7f`) is rejected before URL parsing, as are parser-normalized variants such as mixed-case schemes. The explicit fail-closed special-use policy rejects exact names and subdomains under `.alt`, the entire `.arpa` infrastructure namespace (including reverse DNS, `home.arpa`, AS112, `ipv4only.arpa`, and `resolver.arpa`), `.onion`, `.invalid`, `.example`, `.local`, `.internal`, and `example.com`/`.net`/`.org`. Every raw DNS label beginning with `xn--` is rejected; no IDNA canonicalization or A-label allowlist is currently accepted. Recognizable legacy numeric IPv4 host syntax is also rejected before DNS-label acceptance, including 1–4 component decimal, octal, and hexadecimal forms; this is offline syntax validation, not DNS resolution. `.test` exists only behind the explicit `_allow_test_origin=True` offline-test constructor option and is not expanded by any other setting. DNS resolution/address validation, rebinding defenses, and TLS/transport pinning remain external composition/deployment blockers.

## Authority signer identity configuration

Payment startup now requires an independently reviewed exact pin: `GROWTHMAP_AUTHORITY_ID`, `GROWTHMAP_AUTHORITY_KEY_ID`, `GROWTHMAP_AUTHORITY_GENERATION`, `GROWTHMAP_AUTHORITY_PUBLIC_KEY_SHA256`, and `GROWTHMAP_AUTHORITY_ATTESTATION`. Production must provision these from release review; it must never copy expected values from `LicenseAuthority.handshake()` at runtime. Isolated tests may supply explicit ephemeral fixture identity. Schema 11 stores the pin on both outboxes, checkpoint v2 authenticates it, and Authority inbox receipts bind it. Existing rows never float across generation rotation; legacy pending/leased rows are quarantined for review.

This does not verify the effective packaged desktop public key against the pinned digest. Signed-package/ASAR inspection and exact external match remain required before release.

Delivery acknowledgement requires a durable Authority inbox readback, exact operation/readback response schemas, repeated exact identity checks, and locally recomputed canonical receipts. An object that only returns the correct handshake and a fabricated response cannot advance payment state. Migration 011 labels every historical row `legacy_identity_unproven`; old pending work is quarantined and old delivered fast paths fail for manual reconciliation rather than borrowing current configured identity.

Configure `GROWTHMAP_AUTHORITY_PUBLIC_KEY_FILE` independently from the Authority endpoint. Its exact PEM SHA-256 must match `GROWTHMAP_AUTHORITY_PUBLIC_KEY_SHA256`; Payment verifies strict 64-byte base64 Ed25519 acknowledgements under operation-specific domains. Refund/fence races after an Authority commit enter durable compensation: payment stores the signed entitlement evidence and creates idempotent revocation work, including response-loss retry/readback recovery.

`reconcile_pending` is represented durably as quarantined state plus the exact reconciliation marker so it remains compatible with the historical state CHECK. Workers reclaim it after restart for `payment_confirmed` and `refunded`; refunded work is readback-only and cannot create a post-refund license. Missing readback stays retryable/manual-alert rather than losing the compensation route. File-read errors for `GROWTHMAP_AUTHORITY_PUBLIC_KEY_FILE` are generic and cause-suppressed.

Reconciliation state is the dedicated `entitlement_outbox.reconciliation_phase`, never `last_error_hash`. Workers persist `crossing_maybe_committed` before crossing, then use readback-only recovery after any uncertain result. Refund atomically preserves this phase. Allowed monotonic transitions are schema-enforced; `manual_review` is terminal but queryable and denotes unresolved possible external entitlement.

Reconciliation phases are `none → crossing_prepared → crossing_authorized → readback_only → manual_review`. Prepared may be cancelled only by a refund that wins before authorization. Schema triggers require verified leased context, same lease/fence for authorization, and attempt threshold for manual review. The admin reconciliation endpoint returns at most 200 non-secret rows; license IDs appear only after authenticated acknowledgement evidence exists.

Expired authorized leases are reclaimed readback-only. `crossing_prepared` cannot be retained while changing owner, expiry, state, or fence, preventing two-step authorization forgery. Reconciliation listing reports `evidence_status`; `license_id` appears only after local Ed25519 re-verification of complete delivered evidence.

Prepared crash recovery never mutates owner/fence while retaining prepared. It CAS-cancels the exact expired, evidence-free prepared lease to `none`, then starts a fresh lease only for payment-confirmed orders. This preserves the two-step bypass defense and permits restart convergence.

Security-sensitive lease recovery validates exact canonical timezone-aware UTC timestamps before CAS. A malformed selected lease is treated as checkpointed corruption and fails loudly without mutation rather than being considered expired.

## Production dependency review manifest (evidence index only)

`growthmap_payments.production_composition.load_production_review_manifest(...)` verifies strict canonical schema/domain v2. Its exact plain-dict `trusted_policy` is caller-pinned and immutable-by-copy: a canonical policy ID and computed digest cover every identity’s exact raw Ed25519 public key, one explicit role, and nonempty organization. The manifest must exactly match that policy. The producer must have only `producer`; each dependency must have exactly one `security_reviewer` and one `release_reviewer`, using distinct identities, keys, and organizations, and neither reviewer may be the producer. Policy digest/ID, producer and reviewer fingerprints, reviewer role, release/config/dependency pins, and `ceremony_context_id` are bound into each domain-separated signature. The immutable result exposes the exact selected policy, fingerprints, roles, and organizations.

`ceremony_context_id` is only an expected caller replay-context pin. It does **not** prove uniqueness, freshness, issuance, execution, or a real ceremony; an authenticated external ceremony record remains a blocker. Version 1 and its old `ceremony_id` field are rejected. The public `approval_statement` is a signing convenience wrapper; the verifier uses its private canonical builder, but Python module integrity is not claimed as a security boundary. Files require a trusted local POSIX filesystem; all parsing, read, metadata, and close failures fail closed behind one generic error.

Even cryptographically valid approvals are **necessary but insufficient source evidence**. They do not authorize runtime or prove effective deployed dependencies, transport authorization, key custody, ceremony execution, monitoring readiness, backup restoration, deployment identity, or deployment approval. No manifest/policy secret or private key is accepted. This module is deliberately not read by `create_app()` or `from_env()` and does **not** lift either unconditional production hard-block. Production remains NO-GO pending real ceremony evidence, effective deployment identity, fresh independent authorization, QA, and Security review.

A deterministic external-input schema/template and operator draft are provided at `deployment/production-input.schema.json`, `deployment/production-input.template.json`, and `../../docs/GROWTHMAP-X402-PRODUCTION-RUNBOOK.md`. They contain names and pins only, never secret values. They intentionally do not implement authorization: the repository has no independently authenticated deployment-authorization verifier, no concrete authenticated Authority transport, and no trustworthy measurement contract binding constructed runtime dependencies to reviewed deployed bytes. Until those external contracts are supplied and independently reviewed, adding a builder that accepts objects would reduce authorization to Python class/duck identity and is forbidden.
